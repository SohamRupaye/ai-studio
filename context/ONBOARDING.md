# Handover — AI Studio

For whoever (human or agent) picks this up next. Read this before `PROJECT_STATUS.md` — that file predates most of what's below and understates/misstates current state in several places (safe to update or delete once this doc is trusted).

## What this project is

AI Studio is a model-agnostic "git for AI-native work" — context (not chat) is the primary object, branches/forks let you fork a conversation's context the way you'd fork code, and it accumulates memory/decisions/artifacts across a project instead of re-explaining yourself to a model every session. Electron + React (renderer) + Node (main process, TypeScript throughout). Started 2026-05-27, solo-built, currently pre-launch, validated against one 18-person startup pilot who confirmed the actual pain point (client → SPOC → design → dev, everyone's AI has different context) is real for them.

**Domain hierarchy (as of 2026-07-06): Organisation → Project → Space → Chat → Branch.** Spaces are functional areas within a project (Design / Development / Business — exactly the pilot customer's handoff boundaries) and each owns memories, artifacts, and chats. A chat is a container; users always work *on a branch* (git semantics). Spaces are also the intended unit of future push/pull handoff between people.

## Product sequencing — don't relitigate this

Decided and validated, not up for debate without a real reason:

1. **Ship the single-user "git for my own AI context" product first.** This is what's architecturally built today (local SQLite, no server, BYOK).
2. **Multi-user comes later as an async push/pull/merge model — explicitly NOT live real-time multiplayer.** The actual workflow described by the pilot customer (client sends docs → SPOC hands off → design → dev) is sequential handoff, not simultaneous editing, so it maps to git's async model, not Figma/Google-Docs-style live collab. `packages/prompt-engine`'s branch-diff logic (finds unique/conflicting decisions between branches) is already most of what "merge" would need — reuse it rather than building conflict resolution from scratch when this gets built.

**What changed 2026-07-10 (later) — MCP OAuth actually works now (it never did):**
- **Root cause of "Reconnect does nothing"**: the OAuth flow was never implemented — `MCPManager.startAuth`/`finishAuth` were "simplified" stubs nothing called (no `mcp:authenticate` IPC, no callback server, `needs_auth` never carried a URL so the UI's Authenticate button never rendered), and Reconnect just re-hit the same 401 with zero feedback. On top of that the HTTP transport wasn't spec-compliant Streamable HTTP, so even a valid token wouldn't have connected to Notion/GitHub.
- **New `tools-runtime/src/mcp/oauth.ts`** — the full MCP OAuth 2.1 client: RFC 9728 protected-resource discovery (from the 401's `WWW-Authenticate resource_metadata` or well-known paths), RFC 8414/OIDC auth-server metadata (path-aware candidates + default-endpoint fallback), RFC 7591 dynamic client registration (public client, `token_endpoint_auth_method: none`; explicit `oauth.clientId` config bypasses DCR for servers without it), PKCE S256 + state over a **one-shot loopback server** (`127.0.0.1:19876`+, `Connection: close` + `closeAllConnections` on finish so the port actually frees), RFC 8707 `resource` on authorize+token, refresh-token grant. 5-minute flow timeout; re-clicking Authenticate cancels the in-flight flow (last click wins).
- **`MCPClient` is now real Streamable HTTP**: initialize POST is the connectivity probe (the old GET probe is gone), `Accept: application/json, text/event-stream` on every POST, SSE-framed POST responses parsed (interleaved notifications routed to the normal handler), `Mcp-Session-Id` captured and echoed, `MCP-Protocol-Version` echoed post-negotiation (init sends 2025-03-26), notifications sent id-less and tolerant of empty 202 bodies (previously `resp.json()` crashed). **Tokens attach for any http/sse server with a stored entry — no `oauth` config opt-in** (quick-connect never set one, so tokens would never have been sent). On 401 with a refresh token: silent refresh + single retry before surfacing `needs_auth`.
- **Auth-store sharing gotcha (fixed by construction): `MCPAuth` caches its file after first load**, so separate instances go stale on each other's writes. Manager and all its clients now share one instance (client/manager constructors take an optional `MCPAuth`, which is also the test seam — it takes a file path override so tests never touch `~/.ai-studio/mcp-auth.json`).
- **Wiring**: `mcp:authenticate` IPC (main opens the system browser via `shell.openExternal`, awaits the loopback callback, reconnects, re-registers tools) + `mcp:changed` push on every manager status event (renderer listener invalidates queries — mounted in App.tsx like `models:refreshed`). Explicit user Remove now also forgets stored tokens (`removeServer({forgetAuth})` — the internal remove inside add/reconnect deliberately keeps them).
- **How Dia/VS Code/Claude connect to GitHub & Slack via OAuth anyway (researched + verified 2026-07-10): pre-registered clients.** Those vendors registered an OAuth app with each provider once and ship its client id (the official slack-mcp-plugin publicly ships app id `1601185624273.8899143856786` with a localhost redirect; GitHub tracks DCR as an open feature request — github/github-mcp-server#1404/#2532). To light this up per preset, register an app with each provider (redirect URI `http://127.0.0.1:19876/callback`) and put its id/secret on the server's yaml entry — no UI for this yet, deliberate until the product has its own registered apps. Slack caveat for whoever tries: Slack's v2 OAuth splits `scope` vs `user_scope` params; if sign-in reaches Slack but scopes misbehave, that's where to look.

## Quick facts

- Package manager: Yarn 4 workspaces + Turborepo. `make help` for common commands.
- Native module gotcha: `better-sqlite3` gets rebuilt for Electron's ABI by the `postinstall` hook on every `yarn install`, which breaks plain-Node `vitest` runs until you rebuild it for Node again (`cd node_modules/better-sqlite3 && npm run install`). After testing, restore the Electron ABI with `node node_modules/@electron/rebuild/lib/cli.js -f -w better-sqlite3` (the `yarn rebuild:electron` script exists but yarn doesn't resolve the binary — run it via node as shown). Recurring friction, not a regression.
- The user usually has `yarn dev` running while iterating (vite on 5173 + Electron). A second `electron-forge start` exits silently (port fallback + single-instance), so an agent can't launch its own instance to verify — renderer changes hot-reload into the user's instance, but **main-process changes need the user to restart `yarn dev`**. Say so explicitly whenever main/, packages/event-bus, or packages/database change.
- **Vite dep-optimizer gotcha**: the renderer prebundles npm deps into `apps/desktop/node_modules/.vite`, and that cache does NOT invalidate when a workspace package's dist rebuilds (no version bump) — adding a runtime export to a `packages/*` package then importing it in the renderer throws "does not provide an export named …" at load. `@squirl/shared` is excluded from optimizeDeps for this reason (its dist is dependency-free ESM); if another workspace package grows renderer-imported runtime exports, exclude it too. One-off fix: delete `apps/desktop/node_modules/.vite` and restart `yarn dev`.
- `rtk` (a CLI proxy in this environment) intercepts `find`/`grep` as shell functions and can return stale/garbled results, including for `command find`/`command grep`. If a `find`/`grep` result looks wrong, re-verify with an absolute path (`/usr/bin/grep`, `/bin/ls`) before trusting it.
